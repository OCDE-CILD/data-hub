Methodology & Notes

Every dashboard on the OCDE Data Hub is built from data files published by the California Department of Education. Before those files reach a dashboard, OCDE's Research, Evaluation, and Data Insights (REDI) team runs each source file through a standardized cleaning pipeline: detecting and flagging suppressed values, standardizing school and district identifiers, mapping demographic groups to a consistent set of labels, and validating the result before it's published. This page documents that process in detail — including field-level suppression logic, encoding schemes, and known quirks or limitations by year — for anyone working directly with the downloadable data files. Click on any topic below to expand its notes.

General Data Handling

A handful of conventions are shared across nearly every file on this site:

  • Suppression detection. The specific mechanism has evolved over time. For most years, the columns subject to suppression in a given file are fixed in the cleaning script based on that file's known structure (e.g., a specific named list of count/rate columns to check). Starting with the 2024-25 refresh of some files, this was replaced with an automatic scan: every column is checked for the suppression marker, and whichever ones are found to contain it are treated as suppressible for that run. Either way, the result is the same kind of output — a suppression flag column, and the marker itself replaced with NA — so this mainly matters if you're comparing cleaning scripts across years rather than just using the published data.
  • Type coercion. Once suppressed values are set aside, remaining fields are coerced to numeric or integer types (integer when a column's non-missing values are all whole numbers, numeric when decimals are present), so downstream analysis doesn't have to first parse strings.
  • Demographic group standardization. Each source file uses its own internal numeric codes for student groups. These are remapped to a single canonical set of group labels and numeric codes (demo_group_num) used consistently across every file on this site, and the mapping is validated against a cross-tabulation of raw-to-canonical values to catch any group that fails to map cleanly. This is what lets you compare, say, English Learner outcomes across Chronic Absenteeism and Suspension files with confidence that "English Learner" means the same underlying group in both.
  • Organization level encoding. Records are tagged with a standard reporting-level code — org_level_num: State (1), County (2), District (3), School (4) — so the same file can support state-, county-, district-, or school-level analysis without separate files per level.
  • Charter & DASS status. Charter status is standardized as charter_num: Yes (1), No (0), All schools (2). Where a file distinguishes schools under alternative accountability status, the same pattern is used for dass_num.
  • County-District-School (CDS) codes. Location identifiers are padded to CDE's standard fixed-width CDS format and combined into a single cds field. Occasionally the same numeric code is issued at both the school and district level — an artifact of how CDE assigns codes, not a data error. When this happens, 99999 is added to the affected school-level code to disambiguate it from the district-level record, and the full list of altered codes is retained so the substitution can be traced back if needed.
  • Published file structure. The CSV available for download on this site is a user-facing version of the underlying fact table: internal modeling-only fields (alternate demographic group IDs, the pre-conflict-resolution CDS values) are removed, while the padded, usable identifiers (cds, the canonical demographic code) are retained so the file is still fully joinable to CDE's own published files.

Suppression

Suppression is checked at the row level, not field-by-field. For 2018-19 through 2023-24, the columns checked were a fixed list written into the script — enrollment_num, chronic_count, chronic_rate. Starting with the 2024-25 refresh, this switched to an automatic scan that checks every column for the asterisk marker rather than a fixed list — functionally similar in most cases, but able to catch a newly suppressed field that the fixed list wouldn't have anticipated. Either way, a single flag column, suppression (1/0), is set to 1 for a record if any checked column for that record contained an asterisk, which is then removed before the field is coerced to numeric.

Identifiers & CDS Codes

County-District-School (cds) codes are built and padded to a fixed width from the raw county/district/school codes. Where the same numeric code is used at both the school and district level, the school-level version is altered to keep the two distinct, and the list of affected codes is retained as altered_cds.

This resolution is applied to the fact table used to build the dashboard, but not to the "full" CSV — and this has been true in every year checked, not just the current one. The full/flat CSV — the more human-readable export intended for outside analysts — has its cds column rebuilt from scratch after the conflict-resolution step, without reapplying the fix. If you're working with a downloadable CSV directly and joining on cds, be aware that a small number of school/district codes may not be unique in that file, even though they are in the version behind the dashboard.

Demographic Groups & Primary Key

student_group is mapped to the site's canonical demo_group_num scheme and validated to confirm every group mapped successfully. The fact table's primary key is cds + demo_group_num + charter_num, plus dass_num starting in 2021-22 once that field exists.

Identifiers & Structure

The school-year label (e.g., "2018-19") is recoded to a two-digit integer (19) for easier sorting and filtering. Records receive the standard canonical demographic mapping and cds construction described above. The fact table's primary key is the combination of cds, demo_group_num, charter_num, and dass_num — meaning a single combination of school/district, student group, charter status, and DASS status should never appear more than once in the file. Separate entity/district/school dimension tables are built alongside the fact table.

Gender Categories

CDE documentation indicates the GX gender code (non-binary) was not introduced until 2019-20. Rather than assume how a 2018-19 record would have been coded had the category existed, any 2018-19 record that would fall under GX is coded as missing for gender instead of being reassigned to an existing category — this avoids silently inflating or understating any gender category with data that predates its definition.

Identifiers & Structure

Demographic groups are mapped to the canonical demo_group_num scheme and validated the same way as other files. The fact table's primary key is cds + demo_group_num + charter_num + dass_num, matching the Suspension file's structure. Entity/district/ school dimension tables are built alongside it, with district and school codes coerced to integer before primary keys are validated and the dimension objects are cleared from memory.

2018-19: Percentages Only

The 2018-19 file contains percentages only — there is no underlying count field, and percentages are not equal to percent × tested, so counts cannot be reliably back-calculated from this year's file. All suppression in 2018-19 is marked with a single symbol, *. Percentages are converted to decimal proportions during cleaning (e.g., 68.7 becomes .687).

A blank mean_scale_score when grade = 13 (the "all grades" rollup) is expected and is not suppression — CDE simply does not report a mean scale score for that combined row. True suppression of mean_scale_score for small groups/grades is tracked separately via two flag columns, blank_mean_score and mean_score_suppression, so the two cases (not applicable vs. suppressed) can be told apart programmatically.

2023-24: Structural Changes

Several changes were introduced in the 2023-24 file relative to 2018-19:

  • A count field was added for every achievement level in both the core and area test columns.
  • New _total columns were added; reported percentages are calculated as count / _total.
  • Suppression markers are more varied — values may appear as *, an empty string "", or NA, rather than a single consistent symbol.
  • Suppression follows a clear hierarchical pattern, but it is not strictly one-directional:
    • Whenever core enrollment is suppressed, all core testing and area enrollment data are suppressed as well.
    • Core enrollment can be reported while core testing and area data are still suppressed.
    • Core data can be fully reported while area enrollment and area test data are suppressed.
    • Area test data can be suppressed even when area enrollment data is not.
